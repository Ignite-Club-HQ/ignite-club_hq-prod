- Entry-chunk rule: files reachable at app start (App.tsx, layout, app-wide hooks/libs) must NOT statically import @/live/features/*, live/domains, live/icpAgent, live/piiVetKeys, live/identityAccess, or @icp-sdk/* — use await import() at the (async) call site. Why: static imports pull the whole ICP SDK + candid bindings (~760KB rendered) into the boot chunk even when no canisters are configured.
- ICP Cloud Engines: an approved target of kind icp-cloud-engine carries its own host + canisterIds inside backend_routing_config; a country pinned to it (countryTargets) makes getActiveIcpTarget() return that engine via the resolver registered in loadBackendRouting.ts (targetRegistry stays Supabase-free). An engine-assigned country never falls back to mainnet — a disabled/incomplete engine yields empty canisterIds so the user lands on Supabase. Why: residency-driven countries must not touch the public mainnet. Deploy per engine with DEPLOY_TARGET/ICP_ENV on scripts/deploy-mainnet.sh.
- Event map embeds use the connector's public browser key forwarded to IGNITE_LIVE_GOOGLE_MAPS_BROWSER_KEY by both preview scripts (with a hardcoded public fallback because .env is gitignored and publishing may not inject connector vars); never use a server key in the iframe, and offer a Maps link when the browser key is absent so locations remain usable.
- Club media under `clubs/<clubId>/` is encrypted to the shared club identity (piiVetKeys.encryptClubMedia, no per-file pii record) when club_media_lock_version exists; vault uploads pass lock:"own" because the club lock admits every member, not just staff. Decrypt tries the cached club key first, then the legacy per-file key. Why: per-photo derivations were slow and drained cycles.
- Club photo keys persist on-device for 30 days and still-encrypted photo bytes are kept in the Cache API for 7 days (live/deviceMediaCache.ts), both scoped to the principal; removing a club prunes its key and saved photos. Why: repeat visits skip the slow, paid key fetch and the download; trade-off is up to 30 days of a saved club key on a device, while ciphertext is re-read through an authorized read on every open.
- getCurrentInternetIdentity must wait (bounded 20s) for the shared warm-up when a stored II session exists, and answer null instantly when signed out; App.tsx kicks warmInternetIdentityAuthClient alongside the placement load (gated on the stored session). Why: instant nulls before the auth client existed forced callers into fail-and-retry loops that stacked ~13s onto cold chat opens.
- Internet Identity derivation: every address of the ICP frontend canister (icp.net, raw, ic0.app) signs in as https://<id>.icp0.io, listed in the canister's /.well-known/ii-alternative-origins written by scripts/prepare-canister-dist.mjs; this project's DEV Lovable addresses sign in as the DEV frontend canister (listed only in the DEV canister's file, never PROD's). PROD's ii-derivation-origin names https://igniteclubhq.app (members' established identity) and PROD's list admits the canister's icp0.io address. Why: one person must get one identity and profile whichever address or assistant they use.
- Secure-sign-in inbox: club group chats are shown as returned by messaging_domain (membership-enforced canister-side); never filter them through Supabase user_roles, which is always empty for Internet Identity accounts. club_domain account ids arrive as "principal:<text>" — normalize (messagingCandidates.normalizeAccountId) before Principal.fromText or comparisons. Why: both hid or emptied every ICP club chat.
- Native apps (Capacitor) run the bundled dist-live copy; Internet Identity sign-in uses live/nativeInternetIdentity.ts: app-held Ed25519 key, canister-hosted public/native-sign-in.html bridge opened in the system browser, which redirects the same tab to II (ICRC-167 icrc34_delegation; return address /native-sign-in.html allow-listed in ii-auth-callbacks) with the classic pop-up protocol only as a tap fallback — pop-ups from Custom Tabs get blocked or lose the reply, delegation returned via com.igniteclubhq.app://ii-callback (only that scheme is accepted). Why: user wants everything in-app, and the bridge runs on the canister origin so the principal matches the website.
- Phone browsers on the frontend canister's addresses sign in to Internet Identity with the redirect transport (callback `/auth`, allow-listed in `/.well-known/ii-auth-callbacks` by prepare-canister-dist.mjs) and finish the return in product-main before render. Why: the second-tab window flow gets its tab paused on phones and II shows "Connection closed".
- IcpSignInScreen owns login presentation; AuthPage retains provider invocation and redirects to preserve identity, invite and session semantics.
- AuthMethodChoice is an inline controlled tab selector shared by email and secure screens; it switches the existing app provider directly without an intermediate picker, and invite hand-offs retain their established presentation. Why: reduce taps without changing authorization or redirect rules.
- Sign-in footers and profile policy links share legalLinks destinations; open separately to preserve drafts and invite URLs, and reuse destinations for internal legal pages.
- Chat screens must tell "no messages" apart from "you may not read these messages" using the server's own authority (Supabase `can_access_chat_group`, the canister's "…access forbidden" refusal — see features/messaging/thread/chatAccessState.ts); an unknown answer keeps the existing screens and never claims no access. Why: both backends hide forbidden messages as zero rows, so a refused chat looked like an empty one.
