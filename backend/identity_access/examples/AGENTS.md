# identity_access account-lifecycle rules (overflow from identity_access/AGENTS.md; they cover identity_access/src)

- Bound account deletion (prepare/commit/cancel/settle) has its own release gate: `bound_deletion_released()` accepts the rehearsal flag OR `IGNITE_BOUND_DELETION_RELEASE=1`; production sets only the latter so the other rehearsal-gated lifecycle features stay closed. Why: deletion timing was release-approved independently of the remaining cross-group lifecycle work.
- Unlink jobs freeze exact targets before fan-out and validate all acknowledgements before completion; legacy jobs derive targets only from their historically immutable persisted inventory during upgrade. Sync rejects receipt-covered aliases and contradictory equal-version snapshots. Why: registry substitution and delayed replies must not resurrect removed identities.
- identity_access memory 6 retains stable-B-tree principal denials under a 32 GiB memory-derived safety budget (not lifetime 80k quotas) (legacy CBOR defaults to Unlinked); only unlink permits explicit newer same-account reauthorization, while Erased/Rekeyed are terminal and rekey retries require the recorded destination. Memory 7 retains stable-B-tree erased-account versions under the same budget (not lifetime 10k quotas); account access verifies principal membership as well as the index. Validate all subjects/capacity before writes; commit erase/rekey history before mutation and refuse version exhaustion. Eligibility remains local-only consensus evidence, never a grant/global fence. Why: stale indexes/deleted records permit resurrection; old removals and incomplete backups still need attested history.
- AccountAdmission is shared local-only admission, never a resource grant: identity service readers live in separate additive stable memory 8, independently from club unlink authorities; service-reader configuration and subject-bound account reads remain rehearsal-gated. Why: registering a service reader must not make it an unlink receiver or release production account fan-out.
- Legacy private query APIs refuse only when account admission rehearsal is enabled; read_account_* APIs use consensus admission and retain existing permission checks. Worker delivery checks human authors/recipients, not infrastructure principals. Why: query replicas and service caller identities cannot prove the original human current eligibility.
- Expanded admission domains expose additive protected consensus reads while legacy queries close only in rehearsal; delegated permission checks retain trusted-caller validation and use the original human, while internal relationship predicates filter ineligible roster subjects without aborting the requester. Why: infrastructure callers and unrelated recipients are not the requesting account; entry coverage alone cannot establish interrupted-operation or global revocation acceptance.
- Admission coverage lives in docs/account-permission-coverage.md; test-only delayed callbacks require observed holds, admitted positive controls, exact-resource retries and real derived-key decrypt controls. Why: failures alone cannot prove no partial effects, correct keys or globally complete revocation.
- identity_access removal-history consensus readers are rehearsal/governor-only, page ordered denials/erased accounts; group inventories use <=64-key revision-pinned pages across both consensus reads, reject mid-read revision changes, and retain a 4096-row stable-B-tree safety bound; page and frozen unlink intents at a stable memory-9 revision; every lifecycle/denial/erasure/service-reader mutation and upgrade invalidates continuation. Why: legacy export_state omits removal history; this bounded evidence is not restore support, full deployment inventory, admission generation or global drain proof.
- Removal inventory pins registry trust in memory 10 and append-only supplemental service/store placements in memory 11; twice-read consensus group and per-club media registries must match, with history/binding rechecked after each reply and every configured reader/store represented. club_domain's separate read_removal_media_registry permits only its exact env-configured rehearsal identity; the original operator read stays governor-only. Inventory never changes grants, proves operator-omitted endpoint completeness, fences/drains operations or activates scaling. Why: primary-store config and browser-supplied lists cannot establish removal coverage.
- Removal barrier preparation stays governor/rehearsal-only: memories 12/13/14 retain monotonic generation, immutable full-inventory intents and indexed subject fences; no rekey or restored account may bypass them, and config is frozen while any intent exists. There is deliberately no completion/unfence endpoint until every receiver implements authenticated persistent drain. Why: inventory evidence and identity-local denial cannot prove remote in-flight work drained or a rolled-back authority is safe to resume.
- Removal-history consensus pages include the monotonic removal generation, exact account barriers, subject index and receiver receipts alongside denials, erasures and unlink intents; every page is revision-pinned and bounded. Snapshot imports reject fenced principal bytes/text before replacement and never replace receiver maps. Why: an export that omits barriers or restores aliases cannot prove permission-preserving recovery.
- Bound deletion is local-only: memory-16 tickets freeze account/binding and link/unlink/status/rekey changes; router memories 10/11 pin the trusted identity authority and non-expiring locks checked by every registry mutation. Commit checks captured aliases on all clubs and rechecks local state without awaits; only confirmed erasure permits identity settlement. No governor/timeout unlock. Shared workload is identical across groups; routed services are unique. Why: preserve deletion topology without releasing global drain.
