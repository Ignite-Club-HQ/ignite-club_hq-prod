- Motoko toolchain: moc 1.16.1 via `bun add -g ic-mops && mops toolchain use moc 1.16.1` (binary at /root/.cache/mops/moc/1.16.1/moc; /root is wiped on sandbox resets, reinstall then). Per-canister: `cd backend/<c> && mops install`; compile `moc $(mops sources) --enhanced-migration src/backend/migrations --check src/main.mo`; `--enhanced-migration` takes the migrations DIRECTORY as its argument. .did: same invocation with `--idl src/main.mo` writes main.did in cwd, copy over <c>.did. Bindings: `frontend/node_modules/.bin/icp-bindgen --force --did-file backend/<c>/<c>.did --out-dir` for BOTH frontend/src/lab/bindings/<c> and frontend/src/lab/generated-contracts/<c>. Drift: `node frontend/scripts/check-candid-drift.mjs`.
- Deploy-script rule: Motoko canisters take the governor as an install argument — deploy with `--argument '(principal "<deployer principal>")'` at first install. There is no `initialize()`; first-caller-wins does not exist.
- Migration files are immutable once any deploy may have run them: mainnet records applied migrations by name and skips them, so edits to an applied file never execute and later steps trap on missing fields. Add new state via a NEW, later-timestamped migration (partial `func migration(_ : {}) : { var x : T }` is fine).
- New migrations must sort AFTER the newest existing file (never back-date: mainnet skips anything older than its last applied step), must freeze their types inline (never `Types.X` — a later Types change silently rewrites an applied step), and every main.mo stable var needs a migration that introduces it. To verify against mainnet: match the live module_hash to a commit by rebuilding with `icp build`, then `moc --stable-types` both versions and `moc --stable-compatible live.most new.most`.
- Batched read queries (club_domain get_club_profiles/get_teams/list_teams_multi/get_*_subscriptions/list_sponsors_multi; events_domain list_events_multi/get_event_rosters/list_duties_multi; messaging_domain get_mute_preferences/get_group_metadata_multi/list_groups_by_clubs; mini_league_domain get_mini_leagues/list_mini_leagues_by_clubs) back the same-tick coalescer in frontend live/features/batching.ts — callers keep single-id helpers; it falls back per method on older canisters. Batch queries must apply the same visibility check as their single-id twin. Why: per-id fan-out dominated ICP page-open time.
- Every user-facing canister (identity_access + all domain canisters) exposes governor-only `rekey_principal(old, new, dry_run)` that moves one person's stored sign-in ID (Principal fields, `toText` ids, club_domain `"principal:<text>"` ids) to a new one; scripts/move-account.mjs (workflow move-account.yml) dry-runs every canister before writing and writes identity_access last. Any NEW stored principal / principal-text field MUST be added to that canister's rekey_principal. Why: Internet Identity derivation changes gave one person several sign-in IDs, and their clubs/chats/roles must be movable without data loss.
- Account merge: canisters whose rekey_principal can refuse on new-ID data also expose merge_principal (same impl, conflict guard off; keyed rows that collide keep the NEW row). Any new principal-keyed unique collection must get that keep-new dedup. Why: a sign-in ID can already hold data when two IDs must become one account.
- Before running icp-bindgen, rename candid params named `new` to `new_principal` in the copied <c>.did (TS reserved word breaks generated bindings); --out-dir must be the per-canister folder (…/bindings/<c>), never the bindings root.
- Mainnet canister deploy: scripts/deploy-mainnet.sh + deploy/mainnet/icp.yaml + per-canister backend/<c>/canister.yaml (path-based so mops.toml is found at build); the governor principal is baked into those files as init_args/env vars, and .github/workflows/deploy-icp-mainnet.yml seds that sentinel to the deployer identity's actual principal at deploy time (the gwyap-pqop5-…-cae string in the repo is only a placeholder — Internet Identity keys can't be exported, so the workflow generates the key on first run and uploads it as the deployer-key artifact for DEPLOYER_PEM). The script runs the post-install wiring calls and prints the ID table. IDs land in deploy/mainnet/.icp/data/mappings/ic.ids.json — commit it.
- Production account reads gate on recovery/link transitions only; a pending deletion ticket refuses its own account via current_service_account, never other members. Why: one removal must not lock survivors out.
- Any receiver upgrade changes signed lifecycle counts: production readers must refuse with drift until a fresh signed approval; tests re-approve after deliberate upgrades. Why: restored Wasm cannot restore lifecycle evidence.
- Independent external controller fencing is proven only through the real management canister: exclusive handover via `update_settings`, controller-only `canister_status` readback, and refusal of the former operator's re-add, reinstall, upgrade and status read. PocketIC's private `getControllers` is never evidence. A handover must advance the change count, so fencing the witness itself or any participant invalidates a signed review until a fresh acceptance is armed. Why: an operator who can still replace a witness binary cannot be excluded from its own recovery decision.
- A refused management call is judged against a controller reading taken immediately before it, never against the pre-handover reading: legitimate handovers are recorded in the target's own history and grow live memory. Two adjacent reads must agree first, or the test reports live memory as unusable rather than blaming the refusal. Why: pre-fencing memory cannot prove a refusal did nothing.
