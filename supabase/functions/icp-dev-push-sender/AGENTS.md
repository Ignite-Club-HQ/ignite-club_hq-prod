- This directory is the ICP native sender endpoint for TEST and LIVE, each pinned by SUPABASE_URL to its own base queue (LIVE delivers only to the queue's built-in recipient allowlist): content-free wake-ups (ICP outcall or backup check) trigger reservation from that queue; it sends only when the queue's native_push_configuration names this function's derived principal. Why: Firebase access alone cannot authorize queue delivery.
- Pin transport per project: TEST uses the linked Firebase gateway, LIVE uses the ignite-club-hq service account copied in by the [PROD] sender workflow; never import email handlers or use request bodies/parameters for tokens, recipients or text. Why: hosting must not cross backend/account boundaries and wake-ups are not authorization.
- Native transport uses ICP reserve_native_push/settle_native_push exclusively, with generic transient envelopes and no local journal or notification-table access. Why: hosting only handles Firebase authorization/sending; ICP owns durable send authority.
- The sender identity derives in memory from IGNITE_DEV_ICP_PUSH_SENDER_SEED (legacy name IGNITE_DEV_ICP_NATIVE_SENDER_KEY as fallback) only; never reuse browser-test or legacy scheduled-worker keys; TEST and LIVE seeds differ. Why: each sender's permission is recorded separately on ICP.
- Wake-ups get an immediate 202 and delivery continues in the background (EdgeRuntime.waitUntil); a wake-up during a run sets a rescan instead of being dropped. Why: the queue's outcall gave up while the sender waited on consensus calls, leaving alerts uncollected.
- Native draining continues acknowledged ten-send batches within a bounded time budget and stops on uncertain errors; queue-owned wakes resume remaining work. Why: larger audiences must not wait for the backup after every ten alerts or replay a lost settlement.
